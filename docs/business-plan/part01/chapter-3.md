## 第三章 核心问题：人与数字世界之间的 Gap

### 3.1 我们拥有越来越强大的工具，却仍然需要亲自完成大量操作

想象这样一个场景。

一个人结束了一天的工作，准备整理当天的项目进展。他希望系统能够自动收集项目管理工具中的任务状态，整理会议记录，提取沟通中的重要结论，生成一份工作总结，并将结果保存到指定位置。

从人的角度看，这只是一个明确的目标。

但在传统的软件使用方式中，这个目标可能需要经过一系列操作才能实现：

打开项目管理系统，筛选任务，复制进度；打开会议记录，查找关键结论；切换到沟通工具，整理讨论内容；再打开文档编辑器，组织信息、调整格式，最后保存并通知相关人员。

每一个步骤都有对应的软件功能，每一个软件也可能已经很好地完成了自己的工作。

问题在于，这些功能并没有自动组成一个围绕用户目标运转的完整过程。

用户仍然需要理解任务、寻找工具、协调步骤、传递数据，并判断最终结果是否符合预期。

这就是人与数字世界之间的一种距离。

随着软件数量和功能不断增加，人们获得了越来越多的能力，但同时也需要承担越来越多的操作、协调与管理成本。

当任务只涉及一个简单功能时，这种成本可能并不明显。

当任务跨越多个应用、多个数据源和多个执行步骤时，这种成本就会逐渐累积。

因此，ZeroGap 关注的不是某一个按钮是否足够方便，也不是某一个应用是否缺少某项功能。

我们关注的是一个更完整的问题：

**为什么人已经明确知道自己想完成什么，却仍然需要亲自协调大量技术细节，才能真正完成目标？**

### 3.2 第一个 Gap：理解 Gap——系统理解的，不一定是人真正想要的

人类表达需求的方式，通常具有高度的概括性。

我们会说：

「帮我准备一份明天会议要用的项目汇报。」

这句话对人来说很自然，因为人能够结合已有的工作背景，推断出任务涉及哪些项目、会议面向哪些人、需要包含什么信息，以及应该采用什么形式。

但对于智能系统来说，这句话仍然存在许多未明确的条件。

它需要知道具体是哪一个项目，应该使用哪些数据，汇报的时间范围是什么，目标受众是谁，是否存在指定模板，以及哪些信息不应该被包含。

如果这些条件没有明确提供，系统就可能产生错误的假设。

它可能选错项目，遗漏重要进展，引用过期信息，或者生成一份形式完整但实际上无法使用的报告。

这说明，自然语言交互虽然降低了表达需求的门槛，却没有自动消除理解需求的难度。

理解一个目标，不只是识别句子的字面含义，还需要结合上下文、历史信息、业务规则、用户偏好与现实约束。

但上下文也不是越多越好。

无关信息可能干扰判断，过时信息可能导致错误，未经确认的推断也可能被误当成事实。

因此，系统需要解决的不仅是「能否理解语言」，还包括：

- 能否识别目标中的关键条件与限制。
- 能否区分已知事实、合理推断和未知信息。
- 能否判断何时可以继续执行，何时应该向用户确认。
- 能否在任务执行过程中，随着新信息出现而修正对目标的理解。

对于 ZeroGap 而言，理解 Gap 是从人的意图走向系统行动的第一道关口。

我们希望人能够更自然地表达目标，同时让系统具备足够的能力，将自然表达转换成明确、可执行、可验证的任务定义。

### 3.3 第二个 Gap：执行 Gap——给出答案，不等于完成任务

假设一个智能系统已经正确理解了用户的需求。

它知道需要生成一份报告，也知道应该包含哪些信息。

接下来会发生什么？

在很多场景中，系统可以给出一套操作建议，生成所需文本，甚至编写相应的代码。

但用户仍然需要自己打开应用、执行操作、填写数据、保存文件，并确认任务是否真正完成。

这就是理解与执行之间的距离。

例如，用户希望：

「帮我把这批客户资料整理成统一格式，并导入业务系统。」

系统可能能够生成数据清洗脚本，也可能能够解释导入流程。

但真正完成任务，还需要读取数据、处理格式差异、识别异常记录、调用业务系统接口，并确认导入结果。

如果系统只生成了一段说明文字，那么它完成的是信息提供，而不是整个业务目标。

AI Agent 的价值，正是在于尝试连接这两个阶段。

它不仅要理解用户想做什么，还要在获得适当授权后，组织工具与执行步骤，并根据实际反馈推进任务。

不过，执行能力也不能简单理解为「能够调用工具」。

调用成功不代表业务操作成功，接口返回成功也不一定意味着所有数据都正确。某个中间步骤失败后，系统还需要知道是否可以重试、是否需要回滚，以及是否应该暂停并通知用户。

因此，真正的执行能力至少需要考虑以下问题：

- 任务能否被拆分为明确的执行步骤。
- 每个步骤是否具备合适的工具、数据与权限。
- 执行结果是否能够被可靠地获取。
- 出现异常时，系统能否识别、恢复或安全停止。
- 最终结果是否满足用户最初提出的目标。

ZeroGap 希望缩短的，不只是「提出问题」与「获得答案」之间的距离，更是「表达目标」与「实现目标」之间的距离。

**一个真正有价值的智能系统，不应该只告诉人应该怎么做，还应该在合适的条件下，帮助人把事情做完。**

### 3.4 第三个 Gap：协作 Gap——应用彼此独立，任务却是完整的

现代软件生态有一个明显的特点：每个应用通常围绕特定的功能或业务领域进行设计。

日历管理时间，项目管理工具跟踪任务，文档工具组织知识，通信工具传递消息，业务系统维护业务数据。

这种专业化分工是软件生态不断发展的重要原因。

但从用户的角度来看，许多真实任务并不会按照应用的边界进行划分。

用户不会因为一项工作涉及三个软件，就认为自己正在完成三个互不相关的任务。

他关注的是最终目标。

例如，安排一次项目会议，可能需要先查看团队日程，了解项目进度，确认相关人员，再创建会议、发送通知，并更新项目记录。

这些步骤分散在不同的系统中，却共同服务于同一个目标。

在传统工作流程中，人通常承担着系统之间的协调者角色。

人知道应该从哪里获取信息，知道下一步需要使用什么工具，也知道如何将前一个步骤的结果传递给后一个步骤。

随着任务复杂度增加，这种协调工作本身就会变成负担。

而且，不同系统之间往往存在接口差异、身份认证、数据格式不一致和权限隔离等问题。

即使某个 Agent 能够操作一个应用，也不意味着它能够稳定地完成跨应用任务。

这正是跨平台 Agent 需要面对的问题。

ZeroGap 希望探索一种以任务为中心的协作方式：在获得用户授权的前提下，让智能系统能够协调多个工具与服务，组织必要的数据流转，并对整个任务的执行过程负责。

这里的「负责」，不是说系统可以不受约束地代替人做决定，而是说系统需要具备完整的任务状态管理与结果反馈能力。

用户应当能够知道任务进行到哪里、哪些步骤已经完成、哪些步骤遇到了问题，以及哪些操作仍然需要自己的确认。

因此，协作 Gap 的关键并不是把所有软件合并成一个超级应用。

而是让不同的软件在保留各自功能与安全边界的情况下，能够更好地围绕用户的目标协同工作。

### 3.5 第四个 Gap：信任 Gap——系统说完成了，不代表事情真的完成了

随着智能系统逐渐从提供信息走向执行操作，信任问题会变得更加重要。

在普通问答场景中，模型给出一个不准确的答案，用户可能通过进一步询问或自行核实来纠正。

但在任务执行场景中，错误可能直接影响外部系统和真实业务。

例如：

- 系统声称已经发送通知，但实际上发送失败。
- 系统修改了文件，却覆盖了原有的重要内容。
- 系统执行了数据导入，但部分记录因为格式错误而被跳过。
- 系统理解错了用户的意图，却在没有确认的情况下执行了不可逆操作。

这些情况说明，智能系统的可靠性不能只通过回答是否流畅来衡量。

我们需要区分几个不同的状态：

**理解了需求，不等于制定了正确的计划。**

**制定了计划，不等于成功执行了每一步。**

**执行了操作，不等于最终结果符合预期。**

如果一个系统只能报告「我已经完成」，却无法提供足够的执行证据，那么用户仍然需要重新检查所有结果。

这样一来，自动化可能没有真正减少工作量，反而增加了核验与返工的成本。

ZeroGap 因此需要把结果验证、权限控制、异常处理和执行记录纳入产品设计。

系统应该尽可能基于实际返回结果判断执行状态，而不是仅凭自身生成的文本宣布任务成功。

对于不同风险等级的任务，也应当采用不同的控制方式。

低风险、可撤销的操作可以在授权范围内自动执行；涉及资金、敏感信息、重要数据或不可逆后果的操作，则需要更严格的授权、确认与审计机制。

在某些场景中，系统还应该明确承认自己无法确认结果，而不是给出没有依据的确定性结论。

**ZeroGap 要减少的是不必要的人工操作，而不是让人失去对系统的控制。**

信任不是自动化之后再补充的功能，而是智能执行系统能够被真正使用的前提。

### 3.6 更深层的 Gap：输入方式与人的真实意图之间仍有距离

前面四类 Gap 主要涉及理解、执行、协作和信任。

除此之外，还存在一个更加长期的问题：人必须通过什么方式，才能向机器表达自己的意图？

今天，我们主要依赖键盘、鼠标、触摸屏、语音和视觉交互。

这些方式已经相当成熟，并且能够满足大量实际需求。

但它们并不适合所有人，也不适合所有环境。

有些场景下，用户无法方便地使用双手；有些场景下，语音输入不够合适；对于部分行动受限的人群，传统输入设备可能构成实际障碍。

因此，人机交互的长期发展，还需要关注输入方式本身的局限。

脑机接口为这一问题提供了一个值得研究的方向。

通过采集与处理神经活动信号，特定的脑机接口系统可以在限定任务下尝试识别特定状态或控制意图，并将识别结果转换为外部设备的操作指令。

但必须强调，脑机接口并不是能够直接读取任意思想的通用技术。不同方案的能力边界差异很大，识别结果的可靠性也需要通过具体实验来验证。

对于 ZeroGap 来说，脑机接口不是解决所有交互问题的捷径，也不是现阶段跨平台 Agent 得以运行的必要条件。

它代表的是另一个长期探索方向：

当现有输入方式无法满足某些用户或场景的需求时，是否存在更适合的交互通道？

这个问题需要独立的科学研究、技术验证与应用评估。

只有当新的输入方式能够在特定任务中带来可衡量的改善，并且满足安全性、可用性与实际需求时，它才具有进一步产品化的价值。

### 3.7 这些 Gap 并不是彼此孤立的

理解、执行、协作、信任与输入方式，看起来是不同的问题，但它们实际上构成了一条相互关联的链路。

当用户表达一个目标时，系统首先需要理解它。

理解之后，系统需要制定计划并选择合适的工具。

如果任务涉及多个应用，系统需要协调不同工具之间的数据与操作。

执行过程中，系统需要获取反馈、处理异常，并在必要时请求用户确认。

任务结束后，系统还需要验证结果，并向用户说明实际完成情况。

如果输入方式发生变化，系统仍然需要将新的输入转换成能够理解和执行的任务。

可以将这条链路概括为：

**意图输入 → 目标理解 → 任务规划 → 工具协作 → 执行反馈 → 结果验证**

<escape>
用户意图
   ↓
输入与上下文
   ↓
目标理解
   ↓
任务规划
   ↓
跨平台工具执行
   ↓
结果反馈与验证
   ↓
目标完成 / 调整计划 / 请求人工确认
</escape>

这条链路并不一定总是线性执行。

在真实任务中，系统可能需要反复获取信息、修正理解、调整计划，甚至在发现风险时停止执行。

因此，ZeroGap 所关注的不是某一个独立功能，而是整个意图到行动的过程是否能够变得更自然、更可靠、更可控。

这也解释了为什么跨平台 Agent 与脑机接口能够出现在同一个长期愿景中。

跨平台 Agent 主要探索理解之后如何组织和完成行动；脑机接口则探索在特定条件下，能否提供新的意图输入方式。

两者关注链路中的不同环节，但最终都需要回到人的真实需求与可验证的使用价值。

### 3.8 ZeroGap 的问题边界：不是所有距离都应该被消除

当我们提出 ZeroGap 时，很容易产生一种误解：既然目标是让距离归零，那么步骤越少越好，自动化程度越高越好，人的参与越少越好。

但这并不是 ZeroGap 的立场。

在真实世界中，有些步骤确实是多余的。

例如，重复填写相同的信息、在不同系统之间手动复制数据、反复寻找已经存在的内容，都可能通过更好的系统设计得到改善。

但有些步骤具有明确的价值。

重要操作前的身份验证、涉及敏感数据时的授权、不可逆操作前的确认，以及关键决策中的人工判断，都可能是必要的保护机制。

如果为了减少操作而绕过这些机制，那么减少的只是表面上的步骤，增加的却可能是风险与失控的可能性。

因此，ZeroGap 必须明确自己的问题边界。

我们希望减少：

- 不必要的重复操作。
- 应用之间缺乏衔接造成的协调成本。
- 因系统不理解目标而产生的反复沟通。
- 缺乏有效反馈而导致的重复检查。
- 因交互方式不适合用户或场景而产生的额外障碍。

我们不应该消除：

- 保护隐私与数据安全的必要限制。
- 保障用户知情同意的授权步骤。
- 对高风险、不可逆操作的合理确认。
- 人对重要决策、价值判断和最终控制权的参与。

这一区分是 ZeroGap 能否建立长期可信度的重要基础。

**ZeroGap 追求的不是绝对意义上的零步骤，而是让每一个必要步骤都有价值，让每一个不必要的步骤都值得被重新审视。**

### 3.9 如何判断一个 Gap 是否真正缩小了

一个创业理念需要能够被验证。

如果我们只说系统变得更智能了、交互变得更自然了，或者用户体验得到了提升，这些描述还不足以证明问题真的得到了解决。

ZeroGap 需要将抽象的理念转化为可观察、可比较的指标。

对于跨平台 Agent，可以从以下维度开始评估：

**任务完成率**

在预先定义的任务集合中，系统有多少次能够真正达到预期目标，而不仅仅是生成了看似合理的回答。

**人工介入成本**

完成同一项任务时，用户需要进行多少次手动操作、额外确认和异常处理。

**任务耗时**

从用户提出目标到任务达到预期状态，需要多长时间。

**执行可靠性**

系统是否能够识别失败、正确处理异常，并避免将未完成的任务报告为成功。

**结果质量**

最终产出是否满足准确性、完整性和业务要求。

对于脑机接口，则需要采用与具体实验任务相匹配的指标，例如分类准确率、误触发率、响应延迟、跨次使用的稳定性以及用户完成任务的实际表现。

这些指标不能直接混为一谈。不同任务的成功标准、实验条件与风险等级都需要单独定义。

此外，减少操作次数也不能作为唯一目标。

如果某种方案减少了点击，却增加了错误率；如果自动化节省了时间，却让用户无法理解系统做了什么，那么它未必真正改善了整体体验。

因此，ZeroGap 需要关注的是综合效果：

在不牺牲必要安全、控制权和结果质量的前提下，能否减少用户完成目标所需的额外成本？

只有当这一改善能够通过真实任务和可重复的测试得到验证时，我们才能说某一种 Gap 确实缩小了。

### 3.10 本章小结：我们真正想解决的是什么

人与数字世界之间的距离，并不是单纯由点击次数或输入方式决定的。

它存在于意图理解的偏差中，存在于从答案到实际执行的断层中，存在于不同应用之间的协作成本中，也存在于系统结果无法被充分验证时产生的不确定性中。

对于某些用户和场景，传统输入方式本身也可能形成障碍。这为脑机接口等新型交互技术留下了值得探索的空间。

这些问题共同指向一个核心目标：

让用户能够更直接地表达自己想实现的结果，让系统在明确的权限与安全边界内承担更多协调和执行工作，并通过真实反馈证明任务是否完成。

ZeroGap 不打算用一个宏大的概念掩盖这些问题。

我们希望把它们拆解成能够理解、能够实现、能够测试的具体问题，再根据技术成熟度和实际需求逐步解决。

近期，我们可以从跨平台 Agent 入手，验证系统能否可靠地完成一组真实任务。

长期，我们可以持续研究更加自然的输入方式，包括在科学与工程条件允许的情况下探索脑机接口。

不同路线可以有不同的进度，但必须遵循同一个原则：

从真实问题出发，以可验证的结果判断价值。

这就是 ZeroGap 对核心问题的定义。
